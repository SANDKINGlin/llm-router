## Context

**现状**：
- 智能路由池核心功能93%完成，熔断、回退、灰度、探活全部就绪
- 管理完全依赖命令行：改密钥需编辑.env+重启，监控需手动查SQLite表
- 缺乏可视化界面：熔断状态、429统计、健康检查全在数据库，无法实时查看
- 配置调整低效：修改灰度%或阈值需要docker compose restart，中断服务5-10秒

**技术栈**：
- 后端：FastAPI + Python 3.11+ + SQLite + aiosqlite
- 前端：无（当前只有Swagger文档）
- 部署：单容器Docker，进程内多线程(探活+扫描+迁移)

**约束**：
- 必须轻量：个人项目，不想引入复杂前端构建链
- 必须单容器：运维简单，不管理多服务
- 必须安全：密钥不能明文存储，操作需要审计
- 必须可靠：配置修改不能崩服务，需要验证+回滚

**干系人**：
- 运维人员：日常管理密钥、查看监控、调整参数
- 开发者：扩展新功能、调试问题
- 用户：间接受益（系统稳定性和可用性提升）

## Goals / Non-Goals

**Goals:**
1. **管理界面**：提供密钥管理、参数调整、备份恢复的Web界面
2. **监控可视化**：实时展示熔断状态、429统计、健康检查、trace链路
3. **配置热重载**：支持配置修改不重启服务，新请求用新配置
4. **安全机制**：认证鉴权、密钥加密、审计日志、权限控制
5. **轻量部署**：单容器内运行，不引入额外服务或复杂构建

**Non-Goals:**
- ~~用户界面~~：面向外部用户的UI（仅运维内部使用）
- ~~复杂交互~~：拖拽、实时协作、复杂动画（管理后台不需要）
- ~~多租户~~：多组织隔离（个人项目，单一组织）
- ~~实时推送~~：WebSocket实时更新（SSE足够，避免复杂）
- ~~移动适配**：响应式设计即可，不需要移动端专门优化

## Decisions

### 1. 前端技术栈：Jinja2+HTMX

**选择**：Jinja2模板引擎 + HTMX库

**理由**：
- **技术栈一致**：项目已有FastAPI，Jinja2原生支持，不需要额外框架
- **开发速度快**：2-3天可出可用界面，React+Vite需要7-10天
- **部署简单**：单容器，不需要独立前端服务或构建流程
- **维护成本低**：不复杂，Python开发者能维护，不需要前端专家

**替代方案**：
- **React+Vite**：界面更现代，但需要维护两套代码，部署复杂
- **Streamlit**：开发最快，但性能差、受限多、不够专业

**权衡**：牺牲界面炫酷度，换取开发速度和运维简单

### 2. 监控方案：自建Dashboard集成在Admin UI

**选择**：在Admin WebUI内建监控面板，从SQLite读数据直接展示

**理由**：
- **轻量**：不需要Prometheus+Grafana两个新服务
- **统一**：监控和管理在同一界面，不用来回切换
- **够用**：监控需求简单（看状态、查trace），不需要复杂分析

**替代方案**：
- **Grafana+Prometheus**：行业标准，但对个人项目过重
- **扩展Swagger**：最省事，但界面简陋，不适合正式监控

**权衡**：功能有限但够用，避免引入运维复杂度

### 3. 认证方案：localhost默认暴露 + Bearer Token

**选择**：localhost访问免认证，远程访问需要Bearer Token

**理由**：
- **开发友好**：本地开发不用登录，提高效率
- **安全可控**：远程访问必须认证，token有效期24小时
- **简单实用**：不需要OAuth、用户注册、权限管理复杂体系

**替代方案**：
- **Basic Auth**：更简单，但浏览器不缓存，每次都要输密码
- **OAuth2**：更安全，但对个人项目过重，需要额外provider

**权衡**：适合个人项目，多租户场景需要OAuth

### 4. 密钥存储：SecretStore抽象 + 加密后端

**选择**：抽象接口SecretStore，支持环境变量和加密文件两种后端

**理由**：
- **灵活性**：开发环境用EnvSecretStore（简单），生产用FileSecretStore（加密）
- **安全**：支持AES-256加密，密钥从专用环境变量获取
- **可测试**：注入测试密钥，不依赖真实环境变量

**实现**：
```python
class SecretStore(ABC):
    @abstractmethod
    async def get(self, provider: str) -> Optional[str]: ...

    @abstractmethod
    async def set(self, provider: str, key: str) -> None: ...

class EnvSecretStore(SecretStore):
    # 从环境变量读取，set操作更新进程env

class FileSecretStore(SecretStore):
    # 从加密文件读取，set操作AES-256加密后写入
```

### 5. 配置热重载：SIGHUP + inotify watch

**选择**：同时支持信号触发(SIGHUP)和文件监听(inotify)

**理由**：
- **标准实践**：SIGHUP是Unix约定，符合运维习惯
- **自动响应**：watch机制自动检测配置变化，延迟3秒防连续编辑
- **可控开关**：CONFIG_WATCH环境变量控制watch是否启动

**流程**：
```
配置文件修改 → inotify事件 → 延迟3秒 → 重新加载 → 验证 → 应用新配置
                                                  ↓失败
                                            保持旧配置+记录ERROR
```

**并发保护**：重载期间设置锁，30秒超时保护

### 6. 前后端分离架构：双端口设计

**选择**：业务API(:8789)和管理API(:8790)分离

**理由**：
- **安全隔离**：管理接口独立认证，不影响业务API性能
- **灵活部署**：未来可以单独对管理接口限流或隔离
- **清晰职责**：业务API专注路由，管理API专注运维

**实现**：
- :8788 - healthz（健康检查，无认证）
- :8789 - /v1/chat/completions（业务API，无认证）
- :8790 - /admin/*（管理API，需认证）

### 7. 备份方案：tar.gz打包 + 增量支持

**选择**：完整data/目录打包为tar.gz，支持增量备份

**理由**：
- **简单**：tar.gz标准格式，任何工具都能解压
- **完整**：一次导出所有数据（SQLite数据库+配置文件）
- **灵活**：支持脱敏导出(api_key掩码)、增量备份、加密备份

**流程**：
```
导出 → 打包data/ → 可选掩码 → 可选加密 → tar.gz流
导入 → 验证格式 → 自动备份当前 → 解压 → 替换data/ → 重启服务
```

## Risks / Trade-offs

### Risk 1: Jinja2+HTMX学习曲线

**风险**：团队不熟悉HTMX，开发效率可能不如预期

**缓解**：
- HTMX概念简单，通过属性驱动(hx-get/hx-post)，半天可上手
- 社区有FastAPI+HTMX示例项目，可直接参考
- 先做密钥管理面板验证可行性，再全面铺开

### Risk 2: 配置热重载竞态条件

**风险**：重载期间新请求可能拿到不一致的状态

**缓解**：
- 重载锁保护，串行处理重载请求
- 进行中请求用旧配置，新请求等待重载完成
- 30秒超时保护，避免重载卡死
- TDD验证并发场景

### Risk 3: SQLite并发写冲突

**风险**：多个管理操作同时写SQLite可能锁冲突

**缓解**：
- SQLite允许并发读，单写通过WAL模式支持
- 关键操作(asyncio.Lock)保护，避免同时写
- 写失败自动重试(最多3次)

### Risk 4: 密钥加密后密钥丢失

**风险**：SECRET_ENCRYPTION_KEY丢失导致加密密钥无法解密

**缓解**：
- 文档明确说明密钥必须备份到安全位置
- 提供密钥轮换机制，可以重新加密
- 支持降级：密钥缺失时WARNING并降级到非加密模式

### Risk 5: 备份导入破坏生产数据

**风险**：误导入错误备份导致生产数据丢失

**缓解**：
- 导入前强制确认(X-Confirm-Import头)
- 自动备份当前状态到data/.backup/
- 环境隔离：导入文件检查environment metadata，拒绝不匹配导入
- 提供回滚机制：导入失败可从.backup恢复

### Trade-off 1: 界面简单 vs 功能完整

**权衡**：Jinja2+HTMX界面朴素，但足够管理后台使用

**决策**：优先功能完整和开发速度，界面美化是次要需求

### Trade-off 2: 单容器 vs 微服务

**权衡**：单容器部署简单，但耦合紧，未来扩展受限

**决策**：个人项目优先简单，多团队再考虑拆分

### Trade-off 3: 轻量监控 vs 专业方案

**权衡**：自建Dashboard功能有限，但避免引入Prometheus+Grafana

**决策**：当前需求简单，够用即可；未来复杂化再迁移专业方案

### 部署步骤

1. **代码合并**：PR到main分支，通过CI
2. **镜像构建**：docker compose build，包含新依赖(jinja2+cryptography)
3. **灰度发布**：10%流量先切换新版本，观察24小时
4. **全量发布**：确认稳定后全量切换
5. **旧版下线**：保留旧容器1周作为回滚准备

### 回滚策略

1. **配置回滚**：配置验证失败自动保持旧配置
2. **导入回滚**：导入失败从data/.backup/恢复
3. **版本回滚**：docker compose down + 旧版本up，5分钟内完成
4. **数据回滚**：保留最后一次备份，确保可恢复

## Open Questions

### Q1: 密钥加密密钥管理

**问题**：SECRET_ENCRYPTION_KEY存储在哪里？如何轮换？

**选项**：
- 选项A：存环境变量，运维手动管理（简单但风险）
- 选项B：存密钥管理服务（HashiCorp Vault）（安全但复杂）
- 选项C：K8s Secret（仅K8s环境适用）

**建议**：选项A起步，文档明确安全要求；未来如多租户再升级选项B

### Q2: 监控数据保留策略

**问题**：trace_cold表无限增长，需要清理策略

**选项**：
- 选项A：定期清理90天前数据（简单但可能丢历史）
- 选项B：归档到对象存储（完整但复杂）
- 选项C：分级存储（热数据30天+冷数据归档）

**建议**：选项A起步（90天足够历史分析），数据量再大考虑选项C

### Q3: 前端实时更新频率

**问题**：Dashboard数据多久刷新一次？

**选项**：
- 选项A：手动刷新（简单但不实时）
- 选项B：定时轮询30秒（平衡但耗资源）
- 选项C：SSE实时推送（实时但复杂）

**建议**：选项B起步，页面加载时自动拉取，用户可点刷新；需要实时再升级SSE

### Q4: 多环境配置隔离

**问题**：开发/测试/生产配置如何隔离？

**选项**：
- 选项A：多config.yaml文件（config.dev.yaml/config.prod.yaml）（简单但文件多）
- 选项B：环境变量覆盖（灵活但不直观）
- 选项C：配置中心（专业但过重）

**建议**：选项A+B混合：基础配置用文件，敏感信息用环境变量覆盖

### Q5: 审计日志保留时长

**问题**：审计日志保留多久？如何查询？

**建议**：
- 默认保留180天（半年足够审计需求）
- 提供按时间/用户/操作类型过滤查询
- 超过180天自动归档到trace_cold（类似业务数据）
