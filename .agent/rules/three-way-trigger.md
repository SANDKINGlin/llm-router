## 三方辩证触发规则 (本项目 llm-router)

**加入时间**: 2026-07-31 (用户原话 "补充要求")
**适用范围**: 所有本项目 (llm-router) 任务切片
**继承关系**: 本节为全局 `~/AGENTS.md` 三方辩证硬规则的**项目级补充**, 不冲突时按全局, 冲突时本节优先 (因更具体)

### A. 单方执行条件 (不需要三方辩证)

满足以下**所有**条件, 可由主会话 (Codex / Hermes / CC) 单方执行 + 真验:

1. **修复/任务本身已得三方共识**:
   - 在 `~/ObsidianVault/20-记忆/共享/research/` 或 `.harness/evidence/` 有归档
   - 归档里有"三方真审签字位"且 3 份独立报告 MD5 互异
   - 三方对**修复方向/边界/方法**已盖章 (CC ✓ / Hermes ✓ / Codex ✓)

2. **修复边界不超出已共识范围**:
   - 修复的代码/文件/目录 = 共识归档里允许_paths 列表内
   - 修复不会改变走向 (commit 仍在原切片分支/wt 内)
   - 修复不会改变策略 (不切换实现方案, 不切换 rebase/merge/PR 路径)

3. **风险等级 LOW 或 LOW-MEDIUM**:
   - 数据丢失风险 LOW (cp/copy 而非 delete)
   - 接口/契约破坏风险 LOW (validator/script 验证通过)
   - 依赖/兼容性风险 LOW (跟既有实现一致)
   - 测试/验证风险 LOW (本地可跑 + 远程 CI 可验)
   - 操作安全风险 LOW (限定 allowed_paths)

**满足 A.1-A.3 全部**: 单方执行 + 真验, 完成后归档 + 落证据
**参考 precedent**:
- D11 (修 CI OpenSpec Validate 失败) — 跟 B7 (tasks.md 顶部对齐) 同模式, 已归档, LOW 风险 → 单方
- r9.6 (智能路由层跳变规则切片) — 已 r9 总归档三方共识 → 单方增量
- 任何 ".harness/evidence/*.json" 里 verdict=PASS 的切片 → 单方 follow-up

### B. 三方辩证触发条件 (必须频繁三方共识)

满足以下**任一**条件, **必须**走三方辩证 (5 阶段流程):

1. **阻塞问题**:
   - 任何阻塞导致切片无法直接实施 (CI fail / merge conflict / 网络阻 / 验证 fail / 缺依赖)
   - **必须**三方独立探查根因 + 提解法 + Codex 整合 → 不准 Codex 单方裁决

2. **走向变更**:
   - 切片路径跟原计划不同 (例: r9.7 原计划 rebase+push, 实际走 PR 路径)
   - 工作流变更 (例: 单 PR 改多 PR, 直接 push 改走 PR 路径, master 改 fork branch)
   - **必须**三方共识才能变更方向

3. **策略变更**:
   - 实现方案变更 (例: SQLite 改 Redis, FastAPI 改 Flask, wt 改主仓)
   - 验证策略变更 (例: skip pytest, 跳过 E2E, 不跑 validator)
   - push 策略变更 (例: rebase vs merge vs PR 路径, --force vs --force-with-lease)
   - **必须**三方共识才能变更策略

4. **分支任务变更**:
   - 新增分支任务 (例: r9.7 临时拆出 D11)
   - 删除/合并分支任务 (例: r9.5 + r9.6 合并)
   - 优先级变更 (例: P+ 改 P0, 顺序倒置)
   - **必须**三方共识才能变更分支任务

5. **影响以后整体任务进程**:
   - 改动会影响其他切片依赖 (例: rebase 改 35 commit SHA 影响 7 worktree 引用)
   - 改动会改变 master 上游历史 (例: --force-with-lease 覆盖别人 push)
   - 改动会引入新依赖/新端口/新接口/新 CI 触发条件
   - 改动会留 P+ 切片影响后续 (例: CI 失败留 D11 修, D11 又触发 D12)
   - **必须**三方共识才能动整体进程

**满足 B.1-B.5 任一**: 立刻按 `~/AGENTS.md` 三方辩证硬规则跑 5 阶段流程
**关键约束**:
- **不准**单方判断"这是小改, 不需要三方" — 走 B.5 兜底
- **不准**"前次共识涵盖本次" — 必须当前切片独立三方
- **不准**"用户超时自动推进" — 阻塞类 B.1 必须三方, 不准超时豁免

### C. 决策树 (实施前快速判断)

```
要执行的任务 T
├─ T 有三方共识归档? 
│  ├─ 是 → T 修复边界跟归档一致?
│  │  ├─ 是 → T 风险等级 ≤ LOW-MEDIUM?
│  │  │  ├─ 是 → [A] 单方执行 + 真验 ✅
│  │  │  └─ 否 → [B] 三方辩证 (B.5 兜底)
│  │  └─ 否 → [B] 三方辩证 (B.2 走向变更)
│  └─ 否 → [B] 三方辩证 (无共识基础)
└─ T 涉及 B.1-B.5 任一? → [B] 三方辩证 (不必进 A 判定)
```

### E. 触发时落地物

每次 B 类触发必须落:
1. 三方 brief (CC + Hermes + Codex 独立 brief, 不复用)
2. 三方 result (独立命令 + 输出 + 结论, MD5 互异)
3. Codex 整合 divergence-convergence (标 [共识/分歧/BLOCKED])
4. BLOCKED 项必须给用户拍 (按 7-25 第二轮硬规)
5. 归档到 `~/ObsidianVault/20-记忆/共享/research/`
6. 去重索引 (agent-dedup-archive)
